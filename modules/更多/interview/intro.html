introduce ​

我之前主要做的是中台系统前端的架构和工程化，重点在微前端和前端SDK这块。
参与了基于 qiankun 的微前端SDK架构落地，同时设计了一个脚手架，方便快速接入，主要是解决多业务系统接入中台的问题。
通过这套方案，我们把新系统接入成本从原来的几天降低到1小时以内，同时实现了用户权限、菜单、路由、通信等能力的统一。
同时做个chrome代理插件，方便开发调试，实现开发效果实时呈现。避免发布后才能发现问题。
微前端主要就是解耦业务系统与中台能力，大大降低开发难度与系统维护。同时方便业务系统的拓展延伸。
整体来说，我现在更偏向于做前端架构设计和复杂系统落地，而不仅是页面开发。

question ​

🧩 二、微前端核心话术（必问）
❓Q1：为什么要用微前端？
主要是为了解决系统复杂度和团队协作问题。
当时我们的系统是多业务线并行开发，如果用单体应用会导致：
1. 代码耦合严重
2. 发布风险大
3. 团队协作冲突多
所以我们引入微前端，把系统拆成多个子应用，每个应用独立开发、独立部署。

加分一句：
本质上是把前端从“单体架构”演进到“分布式架构”。


❓Q2：为什么选 qiankun？
主要是考虑到生态成熟度和接入成本。
qiankun 基于 single-spa，提供了完善的应用加载、沙箱隔离、通信机制，同时对 Vue 项目支持比较好。
我们可以比较低成本地把现有系统改造成微前端，而不是完全重构。


❓Q3：微前端通信怎么做？
👉 这是重点（你可以直接背👇）

我们主要分了三种通信方式：
1. props传递（主应用 → 子应用）
   用于初始化数据
2. 全局事件（发布订阅）
   用于跨应用通信
3. 全局状态（qiankun提供的globalState）
   用于共享数据，比如用户信息、权限
在复杂场景下，我们会封装一层通信SDK，统一通信方式，避免直接依赖qiankun。

👉 ⭐ 加分点：
“通信不直接暴露 qiankun，而是通过 SDK 封装一层”


❓Q4：微前端有哪些坑？
👉 面试官很爱问

主要有几个：
1. 样式污染
   → 用 scoped / CSS Module / 命名规范解决
2. JS污染（全局变量冲突）
   → qiankun 的 Proxy 沙箱
3. 路由问题
   → 我们自己封装了 history 插件解决返回跳转问题
4. 子应用加载性能
   → 做了预加载和按需加载

🧱 三、SDK设计话术（核心杀招）
❓Q5：为什么要做 SDK？

因为微前端只是解决“拆”的问题，但没有解决“统一”的问题。
如果每个子应用都自己实现权限、通信、路由，会非常混乱。
所以我们抽了一层 SDK，把这些能力统一起来，让业务应用只关注业务。

👉 ⭐ 这句话很关键：
“微前端解决拆分，SDK解决统一”

❓Q6：SDK都做了什么？
主要包括：
1. 权限系统（菜单 / 按钮级）
2. 路由封装（统一跳转）
3. 通信机制（事件 / 状态）
4. 用户信息管理
5. 接入规范
同时我们还配套了脚手架，可以一键生成符合规范的项目。

❓Q7：SDK怎么设计的？
👉 这一段是“架构味最重”的👇

我们把 SDK 设计成一个“中间层”，隔离业务应用和中台能力：
业务应用 → SDK → 中台
这样做有几个好处：
1. 解耦业务和平台
2. 统一接口规范
3. 方便后续扩展
同时我们会做版本控制，保证兼容性。

❓Q8：SDK怎么推广？
👉 这是很多人答不出来的（你可以碾压）

我们通过三个方式推动落地：
1. 脚手架（自动接入）
2. demo项目（示例）
3. 文档体系（接入指南）
这样可以让新团队快速上手。

🚀 四、组合杀招（面试官最爱）
👉 这个问题你可以主动说👇
❓“你觉得你这个项目最有价值的点是什么？”

我觉得有两个核心点：
1. 架构层面：
   从单体应用升级到微前端架构
2. 工程层面：
   通过 SDK + 脚手架，把接入成本大幅降低
最终的结果是：
新系统接入时间从几天缩短到1小时以内

👉 ⭐ 这句话一定要说：
“我们不是做了一个系统，而是做了一套可以复用的能力体系”


🎯 五、反问（加分项）
面试最后你可以问👇：
想了解一下你们现在前端架构是偏单体还是微前端？
如果是微前端的话，目前主要遇到的挑战是什么？

👉 面试官会觉得你是“同行”


🧨 最后给你一个“王炸总结”（一定要记）
👉 如果只能记一句话：
我主要做的是：用微前端解决系统拆分，用SDK解决能力统一。
